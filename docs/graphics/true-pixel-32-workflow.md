# 実32px化 制作・検査標準 — 白妙の実例から

> 対象：『新生 鬼哭の花契り』のNPC／主人公SD／タイル／オブジェクト／装飾。作成時点のリポジトリ仕様を優先し、以下は再現可能な知見として用いる。

## 目的と用語
- **実32px**：最終データの1画素がゲーム内の論理1px。高解像度の「ドット絵風」イラストを指さない。
- **1セル**：32×32px。キャラはセル内の表示領域、オブジェクトは表示寸法と接地・占有マスを別に定義する。大きな建物等は複数セルでよい。
- **原画**：デザインと形を定義する資料。**採用画像**：実寸で目視承認されたゲーム用素材。原画をそのまま採用画像と呼ばない。
- **色ロック**：既存の画素値を保護する制約。肌色、瞳、特定の装飾色、陣営色などの保護対象を制作前に定義する。色域による曖昧な判定だけに依存せず、対象領域や承認済み座標との一致で検査する。

## 白妙で実際に起きたこと（事実と教訓）
1. 高解像度原画や32px化の試行を繰り返すうち、前髪・顔に斑点や縞模様が生じた。元画像の複雑な明暗が小さな画素に残ると、髪束でなく異物に見える。**学び：原画は極力明暗をつけず、形と主要色面を先に決める**。
2. 画像の自動変換や再合成だけでは顔の破綻を直せなかった。実32pxエディタで静止画の画素を確定し、承認済みの形を次工程の正本にした。**学び：破綻しやすい顔・シルエットは目視承認後に勝手に再変換しない**。
3. ユーザーが選んだ `sprite-walk-4dir.json` を基準にして、肌色を固定。静止画の頭部を歩行A・Bに共通化し、足元に動きを残すことで頭の模様がフレームごとに変わる問題を抑えた。**学び：共通部位と可動部位を分離する**。
4. 採用された白妙アトラスは `assets/characters/tenyo-npc-v2/shirotae-walk-96x128.png`（96×128px、3列×4行、各32px）。配列順は列＝静止／歩行A／歩行B、行＝正面／背面／右／左。制作エディタのJSONでは `front/back/left/right` 順もあり、**JSONの方向順とPNGアトラス行順を明示的に対応付ける必要がある**。
5. 実装当初の白妙は高さ約56pxとなり、緋月のSD表示基準28pxのおよそ2倍だった。実装時の倍率の誤設定が原因で、画像の再加工ではない。**学び：採用画像の画素サイズと、描画時の不透明シルエットの実表示高さは別の検査項目**。修正ブランチ `improve/shirotae-match-hizuki-scale` で28px相当へ合わせる処理を作成（この文書はその本編反映・Safari検査を保証しない）。

## 推奨制作パイプライン
### 0. 現物と契約
`AGENTS.md`、`.agents/skills/asset-design/SKILL.md`、対象カテゴリスキルを読み、既存承認素材と実描画経路を取得する。規格を書き出す：
- 対象カテゴリ、承認原画、必要な32pxセル数、最終幅×高さ、視点、透明背景
- 固定パレット／固定領域（肌・顔など）、可動部位、陰影追加可否
- 接地アンカー・占有マス・当たり判定・遮蔽（オブジェクト）
- タイルの接続方向・繰り返し条件（床・地形）
- カメラを含めた実描画倍率／画面での不透明部分の高さと足元

### 1. 原画：明暗より形
- まず輪郭・頭身・衣服などの**大きな面**、素材同士の境界を設計し、同一部位はなるべくフラットな色を使う。
- 自動的なテクスチャ、光沢、細かい髪筋、ディザリング、過剰な陰影は初期原画には加えない。小サイズで意味を持つアクセントだけ残す。
- 無彩色化や暗い輪郭は**自動で必ず付けるものではない**。細部を強調するのは実32px化後。
- 原画が十分に使える場合、画像生成は行わずクロップ・透明化・画素編集で再利用する。

### 2. 実寸32pxへ規格化
- 透明の外接矩形を検出し、縦横比を維持して規定表示領域へ置く。人物は現行のトップビュー規約で原則28px以内、オブジェクトは契約した高さに従う。
- 最近傍または明示的に選択したサンプリング方式で**初回変換候補**を作る。中立的な明度・コントラスト・彩度を初期値とし、無条件の輪郭補正・過剰な自動減色を避ける。
- 必要な小面積の識別色（目、装飾、肌など）は自動減色後に消えていないか検査。パレットは最少色数競争ではなく視認性で決定。
- いきなり4方向や全タイルへ量産しない。**キャラは正面静止1コマ、タイルは基準タイル1枚**でゲーム内の実寸と拡大表示の両方を確認する。

### 3. 画素単位で清書、承認、固定
- 倍率8倍などの最近傍拡大で確認し、修正対象の**論理画素座標**を特定する。拡大画を直接滑らかに描き直して再縮小しない。
- 保護する肌RGBや色・位置が決まったら、**元データを保持したまま**保護領域をマスクして修正する。配色保護と画素配置保護は異なるので双方を検査する。
- 承認済み静止画を正本として保存する。以降のフレーム・方向生成が静止画を変更したら意図した差分以外は戻す。
- 変更ごとの画素差分（変更座標、旧RGBA、新RGBA）を出して、頭・顔・重要装飾に予期せぬ変更がないか検査する。

### 4A. キャラ/NPC：4方向と歩行
- 正面／背面／右／左で頭の大きさ、足元、服の特徴を統一する。実装行順とJSON管理順は明示的にマッピングする。
- 同じ方向の静止／歩行A／歩行Bは頭部・顔の共通画素を保ち、原則、胴や腕・脚の必要な部分だけ変える。部位が実際に揺れる演出だけ意図的に例外を設定。
- 歩行A・Bは左右の足と腕の逆振りで区別し、再生順は静止→A→静止→B（実装の仕様に合わせる）。無意味なちらつきや1フレームだけの頭伸縮を除く。
- アトラスへ収録後、実32pxセルごとの外接矩形・透明余白・足元基準を検査。隣セルからの画素混入や孤立断片を検出する。

### 4B. 地面・タイル：接続と反復
- **キャラの頭部固定・足運びは適用しない**。32×32の境界ごとに意図した接続条件、中心／上下左右／角／T字／十字の役割を定義する。
- 3×3（必要ならより広範囲）に敷き詰め、上下／左右シーム、繰り返しの癖、地形エッジ、禁止組合せを検査する。
- テクスチャを薄くしたい場合も、必要な地形判別色や素材の見分けは保持する。明暗をなくすことと地面を単色のプレースホルダーにすることは異なる。

### 4C. 物体・家具・建築
- 32pxは基準グリッドであり、表示画像と占有マスは一致を強制しない。接地位置・奥行き・遮蔽・入口・通行範囲を別データとして指定する。
- 余白を減らす際も、アンカーを変えない。接地基準に合わせ、前景／背景の表示順とヒヅキのすれ違いを検査する。
- 建築・オブジェクトの特殊ルールは `create-grid-map-art` と各専用スキルに従う。

### 5. 検査ゲート（不合格なら原画再生成より修正を優先）
1. ファイル：幅、高さ、セル分割、RGBA、アルファ二値／意図した半透明、色数、実寸PNGとJSONの画素一致。
2. 保護領域：肌色等の保護対象に意図しない変更ゼロ。変更した画素が宣言した編集領域内にあるか。
3. 表示形：1倍／整数倍、承認済み基準との頭身・輪郭・配色、足元アンカー、周辺オブジェクトとの比較。
4. 動作：4方向・歩行差分・頭の安定、タイルなら3×3と接続、物体なら接地・当たり判定・遮蔽。
5. **ゲーム実描画**：不透明シルエットの高さ・幅・下端を計算または計測し、実際の緋月SDと比較する。32px画像だから32pxに描いてよいとは限らない。
6. 導入：実PNGをGitHubへ送信し、そのblobと読み込み経路を検証。コード構文→Actions→Pages→実機Safariを**独立**して記録。未検査を合格にしない。

## 避けるべき失敗
| 失敗 | 根本対策 |
| --- | --- |
| 顔・頭に模様が現れる | 原画の明暗を抑え、顔／頭の重要領域を固定し、各フレームの差分を検査 |
| 肌色が変化する | 特定色だけでなく保護する元画素座標・領域も指定し、変更画素を突き合わせる |
| 前髪を直して顔が壊れる | 承認済み静止画から出発、ピクセル単位の小さな差分を保存・レビュー |
| 左右向きだけ大きさが違う | 各方向共通の論理基準／外接矩形で表示スケールを揃える |
| ゲーム内だけNPCが巨大・小さい | 原寸・不透明高さ・描画倍率・カメラ倍率・足元を独立に計測 |
| タイルに継ぎ目がある | 3×3反復、4辺・角・隣接構成の目視・機械検査 |
| 旧画像が残る | 現在の読み込み経路とキャッシュ版を検証し、旧素材を勝手に削除せず置換 |
| 「完成」なのにゲームにはない | ブランチ・GitHub実体・CI・Pages・Safariの各結果を別々に記録 |

## 再利用上の原則
この方法が白妙で採用されたことは、他のNPC・床・家具が自動的に完成する保証にはならない。**低明暗の原画 → 実32px化 → 保護色／領域の固定 → タイプ別検査 → 実ゲーム比較**を汎用の軸とし、形・歩行・接続・接地というカテゴリ固有の仕上げは混ぜない。
